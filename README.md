# Детекция автоматизированного сбора данных (bot detection challenge)

Для каждой `cookie_id` из `test.csv` нужно выдать `score` ∈ [0, 1] - вероятность того, что
за кукой стоит сервис автоматизированного сбора данных, а не человек. Разметка и признаки
привязаны к **суточному окну наблюдения**: `window_start_ts <= event_ts < window_end_ts`.

**Метрика - Precision при Recall ≥ 0.70** (`metric.py`, тот же код, что и у проверяющей системы).
Две детали, на которых легко ошибиться: куки с одинаковым `score` обрабатываются одной группой
(разделить их нельзя), и берётся *максимальный* precision по допустимой области, а не первая
точка, где достигнут recall.

## Структура

```
data/train.csv          11 091 кука, окна 6–19 апреля 2026, колонка target (доля ботов 8.1%)
data/test.csv            4 909 кук, окна 20–26 апреля 2026, без меток
data/events.csv.gz     328 905 событий: время, тип, платформа, user_agent, объявление,
                       категория, локация, тип продавца, поисковый запрос и страница, курсор
sample_submission.csv  эталонный формат ответа: cookie_id, score
metric.py              официальная метрика: precision_at_recall(), recall_at_fpr()
quickstart.ipynb       стартовый пример от организаторов (2 признака, P@R 0.095)
solution.ipynb         решение: разбор данных, признаки, валидация, финальная модель
submission.csv         итоговый ответ, который генерирует solution.ipynb
requirements.txt       версии библиотек (Python 3.12)
```

## Запуск

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python metric.py            # самопроверка метрики
jupyter lab solution.ipynb  # Run All -> перезапишет submission.csv
```

Рядом с ноутбуком должны лежать `metric.py` и папка `data/`. У всех моделей зафиксирован
`random_state`, результат воспроизводим.

## Решение

**Идея.** Сигнал есть на двух уровнях: поведение самой куки (сервис работает быстрее и ровнее
человека, обходит много объявлений и регионов, почти не пользуется избранным, курсор ставит в
одно место или не присылает вовсе) и связи между куками (сервис обходит общий пул объявлений
множеством кук: среди других зрителей объявлений бота ~43% - тоже боты, у людей ~9%).

**Подготовка событий.** Берутся только события внутри окна. В train есть события *после* окна -
42% всех событий ботов и вся капча, но в момент прогноза они недоступны, и модель на них
выучила бы утечку. Удаляются ~4.9 тыс. полных дубликатов, `platform` из 11 вариантов
регистра и синонимов сводится к трём (web / android / ios), события сортируются по времени
(в исходном файле порядок перемешан, без сортировки паузы считать нельзя). Пропуски не
заполняются: они структурные, и отсутствие значения само по себе признак.

**Признаки (30 на куку):** тайминги (13), охват контента (7), курсор (4), состав действий (3),
семейство клиента по User-Agent (1) и связи между куками (2) - доля объявлений, которые больше
никто не смотрел, и доля объявлений, которые уже смотрел известный бот из *прошлых* дней.
Последний признак пересчитывается внутри каждого фолда только по меткам обучающей части.

**Валидация.** Тест лежит позже трейна, куки не пересекаются, поэтому сплит по времени:
expanding window, 4 блока по 2 дня, обучение только на прошлом. Отдельно - недельная проверка
(обучение на 6–12 апреля, проверка на 13–19), которая воспроизводит устаревание меток, как в тесте.

**Модель.** `HistGradientBoostingClassifier` - сам обрабатывает `NaN` и категориальный признак.
Бейзлайны для сравнения: RandomForest из quickstart и логистическая регрессия на тех же 30 признаках.

## Результаты

| модель / набор признаков | P@R ≥ 0.7 |
|---|---|
| quickstart RF (2 признака) | 0.095 |
| LogReg (30) | 0.800 |
| HGB, только поведенческие (28) | 0.680 |
| **HGB (30) — финальная** | **0.869** |
| HGB (30), недельная проверка | 0.852 |

Доля ботов 0.081 - это уровень константного предсказания. Основной прирост дают
признаки: поведенческие доводят метрику до ~0.70, связи между куками - до ~0.87. Ожидаемый
результат на тесте около 0.85.

## Ограничения

- **Приложение.** В android/ios нет курсора - самой сильной поведенческой группы, там модель
  опирается только на темп, охват и связи между куками.
- **Зависимость от разметки.** Самый сильный признак использует метки прошлых дней. Устаревание
  на неделю модель переносит без просадки, но без разметки качество упадёт до ~0.67.
- **Известные сервисы.** Положительный класс - «похоже на уже известные сервисы». Новый сервис
  с собственным пулом объявлений и человеческим поведением распознан не будет.
